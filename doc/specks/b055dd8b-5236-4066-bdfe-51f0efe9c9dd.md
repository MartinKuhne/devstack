# Merge Task with the Item Table — Implementation Plan

## Overview

Merge the `AgentTask` entity into the unified `Item` table by introducing `Task` as a new `ItemSubtype`. Remove the separate `AgentTask` entity and table. Tasks will share the Items table with all other work items but use the `TaskStatus` enum (which has finer-grained states: `Prepare`, `Code` vs `InProgress`).

## Current State

- **Item** table: unified with `Subtype` discriminator (Feature, Defect, Maintenance, Enabler, Epic)
- **AgentTask** table: separate entity with own `TaskStatus` enum and unique properties
- **Item** has `ICollection<AgentTask> Tasks` navigation
- AgentTask unique fields: `Deliverable`, `Risks`, `RequiredFollowUps`, `ComplexityRating`
- `TaskStatus` has extra states vs `FeatureStatus`: `Prepare`, `Code`
- `TaskStatusTransitionService` exists but is NOT wired into `TransitionTaskStatusHandler`

## Target State

- Single `Item` table with `Task` as new subtype
- One unified status enum (`TaskStatus`) used by all Items
- Task-specific fields stored directly on `Item`
- No separate `AgentTask` entity or table
- Task transitions validated through `ItemStatusTransitionService`
- GraphQL and MCP APIs updated to use Item-based Task operations

## Implementation Steps

### Phase 1: Domain Model (Tasks 1-2)

**Task 1: Add Task to ItemSubtype + Task fields on Item**
- Add `Task` to `ItemSubtype` enum
- Add `Deliverable`, `Risks`, `RequiredFollowUps` to `Item` entity
- Mark `AgentTask` as `[Obsolete]` with migration note

**Task 2: Consolidate status enum**
- Keep `TaskStatus` as the single status enum for all Items
- Remove `FeatureStatus` (merge states into `TaskStatus`)
- Add `Prepare`, `Code` states; map old `InProgress` → `Prepare` (initially `Code` → `Prepare`)
- Update `ItemStatusTransitionService` to use `TaskStatus` with subtype-specific rules

### Phase 2: Persistence (Tasks 3-4)

**Task 3: EF Core migration**
- Add new columns to Items: `Deliverable`, `Risks`, `RequiredFollowUps`
- Migrate `FeatureStatus` values → `TaskStatus` values
- Add index on `Subtype` for `Task` subtype
- Drop `AgentTasks` table with data migration (copy rows to Items with Subtype=Task)

**Task 4: Remove AgentTask from DbContext and configurations**
- Remove `DbSet<AgentTask>` from `DevStackDbContext`
- Delete `AgentTaskConfiguration.cs`
- Delete `AgentTask.cs` entity file
- Remove obsolete properties from entity

### Phase 3: Business Logic (Task 5)

**Task 5: Update transition services**
- Update `ItemStatusTransitionService` with Task subtype transition rules
- Task-specific allowed transitions: Planning → Ready/Prepare → Code → Review → ReadyForTest → Testing → Done
- Task constraints: Done requires Result; Failed requires Result; Rejected requires RequiredFollowUps or Result
- Merge/eliminate `TaskStatusTransitionService` (its logic moves to ItemStatusTransitionService)

### Phase 4: API Layer (Tasks 6-7)

**Task 6: Update GraphQL layer**
- Add `CreateTask`, `UpdateTask`, `DeleteTask`, `TransitionTaskStatus` mutations operating on Items with Subtype=Task
- Add `GetTasks` query filtering Items by Subtype=Task
- Add `TaskPayload`, `TaskConnection` GraphQL types (reusing Item types with subtype filter)
- Remove AgentTask-specific GraphQL mutations

**Task 7: Update MCP tools**
- Update `CreateTask`, `UpdateTask`, `DeleteTask`, `TransitionTaskStatus` MCP tools to use Item-based operations
- Fix `featureId` → `itemId` naming inconsistency
- Update `GetTasks` to filter by itemId

### Phase 5: Tests (Task 8)

**Task 8: Update and consolidate tests**
- Update `TaskStatusTransitionServiceTests` → merge into `ItemStatusTransitionServiceTests`
- Update `TaskMutationTests` → migrate to Item mutation tests with Task subtype
- Update `EntityModelTests` → remove `AgentTaskTests`, add Task subtype tests
- Update BDD feature files for Task operations
- Update MCP integration tests

### Phase 6: Verification (Task 9)

**Task 9: Build, test, and verify**
- Run `dotnet build src/server` — must succeed with 0 warnings
- Run `dotnet test src/server` — all tests pass
- Verify GraphQL schema integrity
- Verify MCP tool functionality

## Dependencies

```
Phase 1 (Domain) → Phase 2 (Persistence) → Phase 3 (Business Logic) → Phase 4 (API) → Phase 5 (Tests) → Phase 6 (Verify)
```

- Phases are sequential; each phase depends on the prior being complete
- Tests (Phase 5) must validate all prior phases

## Risks

| Risk | Mitigation |
|------|-----------|
| Data migration for existing AgentTasks | Migration script copies AgentTask rows → Items with Subtype=Task, preserving all fields |
| Breaking existing API consumers | Mark old AgentTask endpoints as deprecated with `[Obsolete]` before removal; provide migration guide |
| Status enum change affects existing data | Migration maps FeatureStatus values to equivalent TaskStatus values |
| TaskStatusTransitionService is orphaned | Its logic is merged into ItemStatusTransitionService as part of Phase 3 |

## Complexity: 8/10

This is a significant refactor affecting domain model, persistence, business logic, API layer, and tests. The main complexity comes from:
- Consolidating two status enums into one
- Migrating data from separate AgentTask table to unified Items table
- Ensuring backward compatibility during transition
